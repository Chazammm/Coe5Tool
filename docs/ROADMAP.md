# Focused roadmap

## 1. Accept this source workflow

Version 0.3 supplies a compiled Windows WPF/WebView2 shell, native copy export, close-state guard and partial historical name-index library. Finish the native desktop acceptance checklist, especially actual window/dialog/close behavior and resize/focus checks. The build and headless tests do not replace those checks. Keep the data-excluding ZIP separate from the personal private cache.

Version 0.2 supplies grouped fields, library filters, inline feedback, source disclosures and the narrow optional level insertion. Finish the updated manual browser checklist before treating the redesign as visually/browser-verified. Test actual keyboard/focus behavior, responsive widths, zoom, native pickers and downloaded bytes. Improve boundary/argument diagnostics using upstream evidence. Any broader field additions need explicit context/insertion rules and preservation regressions; keep unknown content opaque.

## 2. Multi-file definitions and useful catalogs

Model root `.c5m`, companion `.c5se` and allowed includes without flattening/reordering them. Track pass/order and duplicate names, then offer qualified reference lookup. Read existing numeric tables/metadata with version provenance; never infer that a named field's range proves an installed ID exists. Continue to complement the official editor rather than duplicate its completion/hover engine.

The 0.3 index supplies historical names only. Next, establish a clean versioned metadata snapshot with IDs, duplicate/variant records and source/origin evidence. Prefer existing CoE5SE runtime metadata APIs in a separately authorized session, or a fingerprinted read-only binary profile with independent validation. The failed current-layout probe is documented; do not turn it into a heuristic extractor. Resolve distribution rights before adding larger bundled data.

## 3. Native test-field integration

Use existing public CoE5SE test APIs. Design a new test-only mod/session that resolves its own unit/weapon/spell, runs only after a user click and closes/restores state. Validate startup/menu context, caller-owned stand-ins, repeated tests and error cleanup first. Use full combat/manual maps for range, timing, targeting and save behavior. The current task did not authorize launching the game.

## 4. VFX support with evidence

First provide catalog names and mode-aware metadata using existing `lookName`/source tables. Then compare native captures for representative impact/projectile modes. A browser asset preview requires rights to use assets plus verified frames, transforms, timing, blending and target coordinates. Keep any illustrative diagram explicitly illustrative. Generic custom effect-asset registration remains a separate source/API investigation.

## 5. Possible plane work later

Only after the spell/weapon workflow and native test route are reliable, consider a separate plane document inspector. Reuse verified newplane/planepiece formats, preserve map text and respect declaration/repetition/placement limits. Existing fallback, nearportal cache, global portal-ID and generation-failure findings in SCRIPTEXT research remain relevant. A plane editor must not imply guaranteed access or exact generation previews from static layouts.
